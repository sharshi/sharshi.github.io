Hey — this page wrote itself.

Well, almost. This page exists because a one-line issue on a task board came out the other side as a branch-scoped draft pull request — no keystrokes in between. Here's the process that made it happen, diagrams and all.

The one-paragraph version

A small automation loop — call it cc-loop — watches a GitHub Project board, where every task is a plain GitHub issue with a few board fields (Status, Priority, Target Repo). When an issue is actionable, the loop resolves which repo it targets, checks out that repo's default branch, and cuts a fresh per-task branch. Then it boots Claude Code in an attachable tmux session with the issue as its brief, and lets the agent read the repo, write code, and commit. When the agent signals it's done, the loop pushes the branch, opens a draft pull request, and moves the issue to In Review for a human. The task you're reading about — issue #25 — went through exactly these steps.

The pipeline at a glance

What actually happens, step by step

  1. A task is filed as a board issue. A human (or another automation) opens a GitHub issue on the Project board with a short description and a couple of fields — Priority and a Target Repo (the task can point at any repo, not just this site). The issue body is the entire spec.
  2. The loop claims the top task and branches. cc-loop picks the highest-priority actionable issue (anything already In Progress first, then Todo), resolves and checks out the target repo's default branch, pulls, and cuts a fresh branch cc/issue-<n>-<slug> — so the working tree never touches the default branch until a human merges.
  3. The agent gets oriented. Claude Code — running in its own attachable tmux window — reads the repo (config, conventions, neighboring files) before writing anything, so the change fits the existing style.
  4. It implements and self-checks. The agent edits files, and where it can, exercises the result to confirm the change does what the issue asked.
  5. It commits, scoped and labeled. A single focused commit lands on the branch, its message referencing the issue number for traceability.
  6. The loop opens a draft PR. cc-loop pushes, opens a draft pull request against the default branch, records the PR back on the issue, and moves it to In Review. A person reviews and merges — the human stays in the loop at exactly the point where judgment matters.

Where the task state lives

There's no database and no queue file. A GitHub Projects board is the single source of truth, and each task is an ordinary GitHub issue carrying a handful of board fields — Status, Priority, Target Repo, a PR link, and a Blocker note. The issue body is the spec; replies to the issue are the feedback channel. Because state lives on GitHub rather than in any one checkout, it can't fork across branches or collide on merge.

Every task walks the same status lifecycle: Todo → In Progress → In Review → Done, with Blocked as the escape hatch when a task needs a human. The loop reads and writes those fields through the GitHub CLI — a small Python script (standard library only) is the whole backend.

The control loop

The interesting part isn't the straight line — it's what happens after the PR opens. The loop only advances a task when the agent writes a done marker; then it pushes and sets the issue In Review. Reply to that issue with a new comment (say, PR feedback) and the next pass resumes the very same Claude session and updates the existing branch and PR — the conversation picks up where it left off. If the agent can't finish, it logs a reason and the issue is marked Blocked for a human to unblock.

Why branch-per-task matters

Isolation is the whole trick. Every branch is cut fresh off the target repo's default branch and ends at a draft pull request rather than a direct push, so per-task branches never stack on each other and an autonomous agent can move fast without ever putting the default branch at risk. The human review at the end is the safety valve: the machine proposes, a person disposes.
